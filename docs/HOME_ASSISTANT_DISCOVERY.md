# Home Assistant Discovery Mapping

This document describes the Home Assistant MQTT discovery payloads generated by
`homie-home-assistant-discovery`.

## Mapping Contract

The mapper has two goals:

- every valid Homie property with a supported Homie datatype becomes a stable
  Home Assistant MQTT entity;
- the generated Home Assistant platform must be safe to infer from Homie
  metadata alone.

Homie describes MQTT datapoints and can also carry human names and node types.
The mapper uses that metadata where it is specific enough: common settable
boolean lights and fans are discovered as `light` and `fan`. When the metadata
is generic or absent, settable booleans fall back to `switch`. Overrides remain
the right place for site-specific semantics that Homie cannot express.

Automatic discovery is complete for the Homie data model supported by this
package. It is not a promise to infer every specialized Home Assistant domain
from generic Homie metadata.

The generated payloads follow Home Assistant MQTT discovery's device discovery
model: a retained device config payload contains the Home Assistant device
object, origin metadata and a `components` object whose entries each declare a
platform, `unique_id`, `default_entity_id` and state or command topics.

## Automatic vs Override Responsibilities

Automatic mapping is responsible for facts present in Homie metadata:

- stable device and component IDs;
- state topics and command topics;
- availability from `$state`;
- datatype-to-platform fallback;
- numeric, enum and boolean format parsing;
- retained/non-retained behavior that affects Home Assistant updates;
- unit preservation and conservative sensor metadata inference.

Overrides are responsible for semantics Homie cannot express generically:

- site-specific boolean semantics that cannot be inferred from Homie
  `type` / `name` metadata;
- custom entity names, icons and object IDs;
- Home Assistant device classes or state classes beyond safe inference;
- platform-specific payloads, command topics, value templates and options;
- disabling entities that should not be exposed to Home Assistant.

The bridge intentionally does not invent Home Assistant `climate`, `cover`,
`lock`, `vacuum`, `button`, `scene`, `siren`, `valve`, `water_heater` or alarm
entities from plain Homie datatype metadata. Those domains need domain-specific
meaning and Home Assistant configuration fields that Homie core does not
standardize.

## Discovery Topics

Device discovery is published to:

```text
<discoveryPrefix>/device/<deviceObjectId>/config
```

The optional diagnostic Homie State sensor is published to:

```text
<discoveryPrefix>/sensor/<deviceObjectId>_homie_state/config
```

All discovery messages are retained with QoS `1`.

## Device Object IDs

The default object id shape is:

```text
<idPrefix>_<homie namespace>_<device id>
```

Examples:

| Homie base topic           | Object id                        |
| -------------------------- | -------------------------------- |
| `homie/5/kitchen`          | `homie_homie_5_kitchen`          |
| `building/homie/5/kitchen` | `homie_building_homie_5_kitchen` |
| `homie/weather`            | `homie_homie_weather`            |

Object id segments are normalized to lowercase alphanumeric underscores.

A device override may provide `objectId` to preserve an existing Home Assistant
MQTT discovery topic during migration. For example, `objectId: "acme_c1"` makes
the main config topic `homeassistant/device/acme_c1/config` regardless of the
Homie base topic.

## Device Payload

The main retained payload contains:

- `device`
- `origin`
- `availability_topic`
- `availability_template`
- `payload_available`
- `payload_not_available`
- `qos`
- `components`

`origin.sw_version` is set from the package version when the default origin is
used.

Legacy firmware metadata can enrich the Home Assistant device:

| Homie metadata | Home Assistant device field                                 |
| -------------- | ----------------------------------------------------------- |
| `$fw/name`     | `model` when no Homie `type` or override model is available |
| `$fw/version`  | `sw_version`                                                |
| `$mac`         | `connections: [["mac", value]]`                             |

Homie v5 device relationships are mapped to Home Assistant `via_device`. When
both `root` and `parent` are present, `parent` wins because it represents the
direct upstream device. When only `root` is present, `root` is used.

## Availability

Availability is based on the Homie `$state` topic:

```text
<homie base topic>/$state
```

`ready` maps to online. Any other value maps to offline.

## Component IDs

Entity component ids use:

```text
<deviceObjectId>_<nodeId>_<propertyId>
```

Overrides may replace the final unique-id/default-entity-id base with
`objectId`, or the full Home Assistant entity id with `defaultEntityId`.

## Platform Mapping

The automatic platform decision tree is the fallback before mapping rules and
exact overrides are applied:

| Homie property state                   | Home Assistant platform                                                | Command topic |
| -------------------------------------- | ---------------------------------------------------------------------- | ------------- |
| non-settable `boolean`                 | `binary_sensor`                                                        | no            |
| settable `boolean`                     | `auto` semantic mapping, or configured `switch`/`light`/`fan` fallback | yes           |
| settable `integer`                     | `number`                                                               | yes           |
| settable `float`                       | `number`                                                               | yes           |
| settable `enum` with parsed options    | `select`                                                               | yes           |
| settable `enum` without parsed options | `text`                                                                 | yes           |
| settable `string`                      | `text`                                                                 | yes           |
| settable `color`                       | `text`                                                                 | yes           |
| settable `datetime`                    | `text`                                                                 | yes           |
| settable `duration`                    | `text`                                                                 | yes           |
| settable `json`                        | `text`                                                                 | yes           |
| non-settable `integer`                 | `sensor`                                                               | no            |
| non-settable `float`                   | `sensor`                                                               | no            |
| non-settable `string`                  | `sensor`                                                               | no            |
| non-settable `enum`                    | `sensor`                                                               | no            |
| non-settable `color`                   | `sensor`                                                               | no            |
| non-settable `datetime`                | `sensor` with `device_class: "timestamp"`                              | no            |
| non-settable `duration`                | `sensor` with `device_class: "duration"`                               | no            |
| non-settable `json`                    | `sensor` with JSON attributes                                          | no            |

The command topic is the Homie property state topic with `/set` appended,
unless a property override supplies `commandTopic`.

The v3/v4 Homie core datatypes are `integer`, `float`, `boolean`, `string`,
`enum` and `color`. Homie v5 adds `datetime`, `duration` and `json`. Homie v3
devices may omit `$datatype`; the bridge follows the v3 convention by treating
that property as `string`. Homie v4 and v5 require a datatype before discovery
can be generated.

## Boolean Mapping

`defaultCommandableBooleanPlatform` controls only Homie `boolean` properties
where `settable` is true and no mapping rule or exact property override selects
a more specific platform.

| Option   | Use when                                              |
| -------- | ----------------------------------------------------- |
| `auto`   | Infer common lights/fans from Homie metadata.         |
| `switch` | The device exposes relays, plugs or generic outputs.  |
| `light`  | Most settable booleans in the mapped root are lights. |
| `fan`    | Most settable booleans in the mapped root are fans.   |

`auto` uses Homie node/property `type`, `name` and id text. It recognizes common
words such as `light`, `lights`, `lamp`, `led`, `fan` and `fans`. Unknown or
generic booleans remain `switch`.

Non-settable booleans are always `binary_sensor` because Home Assistant cannot
command them.

Use `rules` or exact property overrides when one property needs different
semantics from the global fallback:

```json
{
  "namedNodeState": {
    "platform": "light"
  },
  "devices": {
    "homie/5/kitchen": {
      "nodeNames": {
        "ceiling": "Kitchen Ceiling",
        "extractor": {
          "name": "Extractor Fan",
          "platform": "fan"
        }
      }
    }
  }
}
```

Use ordered rules when matching needs to span many properties or depend on
Homie metadata:

```json
{
  "rules": [
    {
      "match": { "path": "lights/*", "datatype": "boolean", "settable": true },
      "platform": "light"
    }
  ],
  "devices": {
    "homie/5/kitchen": {
      "properties": {
        "relay/state": {
          "platform": "light",
          "name": "Kitchen Ceiling",
          "icon": "mdi:ceiling-light"
        }
      }
    }
  }
}
```

Mapping priority is:

1. built-in datatype mapping and boolean semantic mapping;
2. `namedNodeState` for named settable boolean `state` properties;
3. ordered mapping rules;
4. exact device/node/property overrides under `devices`.

## Automatic Coverage Boundaries

The package currently emits these Home Assistant MQTT platforms automatically:

- `sensor`
- `binary_sensor`
- `switch`
- `light`
- `fan`
- `number`
- `select`
- `text`

[Home Assistant MQTT discovery](https://www.home-assistant.io/integrations/mqtt/#mqtt-discovery)
supports more component domains than this, such as alarm panels, buttons,
cameras, covers, climate devices, locks, scenes, sirens, vacuums, valves and
water heaters. Those domains need richer semantics than plain Homie datatype
mapping. Generating them automatically without an explicit convention or
override would create plausible but often wrong Home Assistant entities.

The intended model is:

- automatic mapping for every supported Homie datatype;
- conservative defaults that do not misrepresent a device;
- overrides for known semantics on a specific installation;
- future semantic presets when a stable Homie-to-Home-Assistant convention is
  defined for a domain.

## Number Format

Homie numeric format uses:

```text
min:max:step
```

Examples:

| Homie format | Number config                   |
| ------------ | ------------------------------- |
| `0:100:5`    | `min: 0`, `max: 100`, `step: 5` |
| `0:`         | `min: 0`                        |
| `:100`       | `max: 100`                      |

Invalid or missing numeric format fields are ignored.

## Boolean Format

Homie boolean format may define payloads:

```text
off,on
```

This maps to:

- `payload_off: "off"`
- `payload_on: "on"`

Without a format the default payloads are `"false"` and `"true"`.

## Enum Format

Homie enum format uses comma-separated options. Escaped commas are represented
as doubled commas.

```text
auto,manual,off
```

Settable enum properties become `select` entities when options are available.
If no options are available, the property becomes a `text` entity instead of an
empty select.

## Sensor Metadata

The mapper preserves Homie units as `unit_of_measurement` for sensors and
numbers.

It also infers common `device_class` values when the signal is unambiguous:

| Unit / semantic hint                     | Device class      |
| ---------------------------------------- | ----------------- |
| `°C`, `°F`, `K`                          | `temperature`     |
| `%` with humidity naming                 | `humidity`        |
| `%` with battery naming                  | `battery`         |
| `V`, `mV`                                | `voltage`         |
| `A`, `mA`                                | `current`         |
| `W`, `kW`                                | `power`           |
| `Wh`, `kWh`, `MWh`                       | `energy`          |
| `Pa`, `hPa`, `kPa`, `mbar`, `bar`, `psi` | `pressure`        |
| `Hz`, `kHz`, `MHz`, `GHz`                | `frequency`       |
| `lx`, `lux`                              | `illuminance`     |
| `dBm`                                    | `signal_strength` |

Numeric sensors default to `state_class: "measurement"` unless an override
provides a specific state class.

## JSON Datatype

Non-settable Homie JSON properties become sensors with:

- `value_template: "{{ 'json' }}"`
- `json_attributes_topic` set to the property state topic

Settable JSON properties become `text` entities so Home Assistant can publish
raw JSON strings to the Homie `/set` topic.

## V5 Attribute Diagnostics

When attribute diagnostics are enabled, observed Homie v5 attribute topics are
exposed as diagnostic entities without hard-coding any extension name. This
applies to implementation or extension attributes such as `$fw/version`,
`$stats/uptime` and `$implementation/ota/enabled`.

Core operational and collection attributes are intentionally not exposed as
observed diagnostics: `$state` drives availability, `$description` drives
discovery, `$log` is a non-retained logging stream, `$alert` is user-facing
alert behavior and the bare `$stats` topic is only an index for concrete
`$stats/*` values.

The mapper derives conservative payload metadata:

| Observed payload          | Platform        | Notes                              |
| ------------------------- | --------------- | ---------------------------------- |
| `true` or `false`         | `binary_sensor` | `payload_on` and `payload_off` set |
| integer or float payloads | `sensor`        | `state_class: "measurement"`       |
| JSON object or array      | `sensor`        | JSON exposed as attributes         |
| other payloads            | `sensor`        | string state                       |

It also applies common path-based metadata without binding the package to any
implementation-specific extension. For example, `$fw/version` enriches
`device.sw_version`, `$mac` enriches `device.connections`, `$stats/uptime` gets
seconds/duration metadata, and MQTT dropped counters get
`state_class: "total_increasing"`. Unknown attributes still become plain
diagnostic entities and can be refined with overrides.

Override matching uses the attribute path under the synthetic `diagnostics`
node. For example, `$implementation/ota/enabled` becomes
`diagnostics/implementation-ota-enabled` for exact property overrides. Known
diagnostics use stable, human-readable object ids such as `ota_enabled`,
`firmware_version`, `mqtt_inbound_dropped` and `homie_extensions`; unknown
attributes fall back to an object id derived from their path.

The v5 `$description` payload also contributes derived diagnostic entities for
the Homie convention version, description version and declared extension list.

Homie extension names do not provide a complete machine-readable schema by
themselves. Use overrides to set exact units, icons, device classes, state
classes, names or object ids, or to disable noisy diagnostics. For example,
`$stats/mqttinbounddropped` can be refined with an exact property override keyed
as `diagnostics/stats-mqtt-inbound-dropped`.

## Legacy Stats

Known Homie legacy `$stats/*` topics become diagnostic sensors:

| Homie stats topic | Platform | Unit | Device class  |
| ----------------- | -------- | ---- | ------------- |
| `$stats/interval` | `sensor` | `s`  | none          |
| `$stats/uptime`   | `sensor` | `s`  | `duration`    |
| `$stats/signal`   | `sensor` | `%`  | none          |
| `$stats/cputemp`  | `sensor` | `°C` | `temperature` |
| `$stats/cpuload`  | `sensor` | `%`  | none          |
| `$stats/battery`  | `sensor` | `%`  | `battery`     |
| `$stats/freeheap` | `sensor` | `B`  | none          |
| `$stats/supply`   | `sensor` | `V`  | `voltage`     |

All stats entities use `entity_category: "diagnostic"`.

## Cleanup

Cleanup messages are retained empty payloads. They are emitted when:

- a published device `$state` retained topic is deleted;
- a Homie v5 `$description` retained topic is deleted;
- a v5 description no longer contains valid properties;
- legacy v3/v4 `$nodes` or `$properties` retained metadata removes all valid
  entities;
- a required legacy datatype is deleted or becomes unsupported;
- `reset()` is called on the bridge.

The mapper also emits device discovery transition payloads when some components
disappear but the device still has other valid components. This lets Home
Assistant remove stale entities without deleting the whole device.

## Non-Mapped Homie Topics

The bridge consumes Homie metadata and generates discovery. It does not process
normal property state payloads, does not validate live property values and does
not react to broadcast or alert topics. Home Assistant entities subscribe
directly to the generated Homie `state_topic` and publish directly to the
generated Homie `command_topic`.

Homie v5 `$target` is a device feedback topic for command acceptance and
in-flight transitions. It is not needed to create the Home Assistant discovery
entity, so the bridge leaves it to the device and Home Assistant runtime path.
Future support could expose target state as an optional attribute or diagnostic
entity if a stable Home Assistant convention for it is defined.
